# EIP-8115: Batch priority fees at end of block

Checklist revision: **2** (28 anchors) — see [Revision Notes](https://github.com/ethsteel/pm/blob/main/Templates/EIP-Complexity-Assessment.md#revision-notes)

## Execution Specs

### Specs

[EIP-8115](https://eips.ethereum.org/EIPS/eip-8115)

Stop crediting the priority fee to the fee recipient after each transaction; accumulate the per-transaction fees in the block output and credit the sum once, after all transactions and before [EIP-4895](https://eips.ethereum.org/EIPS/eip-4895) withdrawals. In EELS this is a two-site change (`disburse_gas_fees` accrues instead of paying out; a new `process_priority_fees` settles before `process_withdrawals`) plus the same end-of-block step in the t8n's duplicated block loop. Prototype: [EELS reference PR](https://github.com/spencer-tb/execution-specs/pull/55).

##### State-access ordering within opcode execution

Changes *where inside an opcode's execution* state is accessed, or where gas is charged relative to that access. Because a state access is recorded in the block-level access list only if execution had enough gas to reach it, this ordering is consensus-critical: moving it changes the BAL at every gas boundary of every affected opcode.

- 0. No change to where state is accessed, or to where gas is charged relative to a state access, within any opcode.
- 1. A single opcode's state-access or gas-charge ordering changes.
- 2. Multiple opcodes' ordering changes, or a new state-accessing operation is introduced whose position in the order must be settled.
- 3. The ordering rule changes for a whole class of state-accessing opcodes at once, or what counts as a recordable state access is redefined — requiring existing BAL vectors to be re-derived across opcodes and forks.

*Distinct from "Modified opcodes", which asks whether an opcode's **result** changed. This row asks about the **path to the result**, which is observable even when the result is identical. An EIP can be 0 on that row and 3 on this one.

*Score changes **to** the ordering. Do not score the fact that state accesses are observable — they always are.

*Each boundary must be re-tested against every other dimension that can change the answer (cold/warm, static/non-static, delegated/direct, revert/success), so the case count grows multiplicatively rather than additively. Note this explicitly under Special Considerations.

##### State gas accounting changes

New state gas accounting rules. State gas is the cost of *writing* state, as opposed to accessing or executing it: `StateGasCosts`, `COST_PER_STATE_BYTE`, the block-level state gas budget, and the spill path into execution gas.

- 0. No state gas accounting changes.
- 1. An existing state gas cost or `STATE_BYTES_PER_*` rate is adjusted.
- 2. A new state-gas-charging site is introduced, or the block-level state gas budget or reservoir allocation is modified.
- 3. A new state gas charging mechanism is introduced, or the spill interaction between state gas and execution gas is modified, affecting existing gas tests.

*Harder to test than blob gas: the spill path means state gas cannot be metered independently of execution gas, and some costs (e.g. `NEW_ACCOUNT`) are state-dependent.

#### Special Considerations

The EIP's single sentence of specification under-determines two consensus-visible behaviors — the credit's EIP-7928 BAL representation and zero-fee touch semantics. Until the EIP pins them, fixtures encode the reference implementation's choices: credit at the post-execution block access index, merging with same-account withdrawal changes, performed iff the block processed at least one transaction. The "before withdrawals" ordering is otherwise unobservable (no execution runs between the two, credits commute, and the BAL keeps one final balance per index).

#### Notes

Post-state equivalence means single-transaction (state test) fixtures are unaffected; only multi-transaction blocks observing the fee recipient mid-block, fee-recipient BAL vectors, and fee-recipient-as-sender solvency flip. Mid-block coinbase reads in existing tests can usually be made fork-portable by moving the observer to a following block, as done for the EIP-8037 coinbase-fee test in the prototype.
